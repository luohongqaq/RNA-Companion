# AI 桌宠的记忆与上下文系统：设计笔记

> 更新时间：2026.11.12
>
> 本文档由AI根据本人的设计文档编写，已由个人审核，讲系统**设计与取舍**：为什么这么分层、为什么把检索从模型手里拿走、失败时怎么退。实测数据、指标口径、A/B 对比都在[实验记录](<experimental records.md>)里；回放工具怎么跑见 [replay-guide](../backend/scripts/replay-guide.md)。

---

## 1. 问题定义

聊天助手可以每次从零开始，桌宠不行——它的价值就在“认识你一年了”。这带来三个聊天助手可以回避的约束：

1. **长期记忆**：跨天、跨月的事实与情绪，不能靠一次会话的窗口兜住；
2. **上下文老化**：单次会话聊到几万字必然超窗，必须压缩并交接；
3. **人设稳定**：记忆里如果写的是“用户”而不是“主人”，角色当场就散了。

评测目标也随之改变：不是答对多少题，而是**隔一周还接不接得上话**。这决定了后面整套评估都是行为指标，而不是准确率（为什么不报准确率，见[实验记录的“局限”](<experimental records.md>)）。

## 2. 设计参数

下面这些是写死在代码里的常量，不是实测结果：

| 参数 | 值 | 作用 |
|---|---|---|
| 预检索候选 | daily 3 张 + topic 3 张，合计 6 | 每轮固定给模型的上限 |
| 最终注入上限 | 10 张 / 48000 token | 模型选择的硬顶 |
| 召回工具预算 | 8 次调用 / 单次输出 12000 token | 允许模型补搜，但给上限 |
| 缓存重放 | 5 张近期更新 + 10 张最近已读 | 补连续性，与预检索去重 |
| 衰减 | `score = 0.5 ^ (距今天数 / 7)` | 三周后约出热池 |
| 热池阈值 | 0.1 | 低于此值不参与默认召回 |
| 摘要预算 | 目标 800 / 上限 1000 token，重试 1 次 | 超预算判重写 |
| 交接等待 | 180 秒，轮询 0.5 秒 | 封存后等记忆生产完成 |

## 3. 架构

### 3.1 前后端分离的两个进程

Electron + Vue 3 + Vite 负责桌面壳与角色动画，Python + FastAPI 负责对话、记忆与上下文，两边 HTTP/SSE 通信。

边界很清楚：**前端只管“长什么样、怎么动”，后端只管“记得什么、说什么”**。这样后端可以脱离界面单独起——回放评估直接打 API，不需要开窗口，这对调试和批量评估是决定性的。

代价是多一套进程与打包。

### 3.2 后端分层

- `api`：路由、schema、依赖注入；
- `module`：业务域，每个域内部再分 core / processing / repository；
- `storage`：SQLite、Qdrant、配置。

业务域：chat（会话与回复）、memory_management（记忆生产）、memory_recall（召回 agent）、context_compaction（压缩与交接）、character（角色卡）。**域之间只通过端口和领域模型通信**，召回 agent 完全不需要知道记忆是怎么写进库的。

### 3.3 存储

结构化数据（会话、轮次、记忆文档、快照）在 SQLite；向量在 Qdrant 本地模式。单用户、本地、可整体搬走，这个组合不需要运维。

双写一致性：先写库、再写向量，失败进补偿任务。向量写失败时记忆仍然可读（只是搜不到），不会丢数据。

### 3.4 提示词是拼出来的

固定顺序、按 token 预算切片：系统提示词 → 角色卡 → 上下文规则 → 固定示例 → 注入记忆 → 历史摘要 → 历史对话 → 本轮锚点 → 当前输入。

这个顺序本身就是设计：**人设在前，事实在后，当前输入贴着锚点收尾**。各部分占比与实测见[实验记录的“稳固人设：提示词构成”](<experimental records.md>)。

## 4. 记忆系统

### 4.1 三层模型

| 层 | 粒度 | 记什么 | 生成时机 |
|---|---|---|---|
| daily | 一天一档 | 当天发生了什么、情绪如何 | 会话封存时按 session 生成 |
| object | 一事一档 | 人、项目、偏好的稳定属性 | 事实抽取 |
| topic | 一个持续事件一档 | 背景、来龙去脉、当前状态 | 多日合并 |

举例，用户说“我又熬夜改桌宠了”：

- daily：“昨晚熬夜到 3 点，情绪有点自责”；
- object：“作息习惯：习惯拖到深夜”；
- topic：“桌宠项目：9 月从记忆层开始，反复重构，10 月底决定交付代码”。

**只有 daily 会退化成流水账，只有 topic 会丢掉情绪细节，只有 object 会变又多又干巴。** 三层是分工，不是冗余；召回时按需组合。

并且一大特点是daily是让模型带入角色来写的（角色的第一人称日记），object和topic不带入只记录真实发生的事情（但称呼保持一致，实测这里用用户，那里用个人定制的称呼，人设会漂移，应该统一）。

### 4.2 什么时候写

会话封存时写，不是每轮实时写。三个原因：

1. 实时写会让每轮多一次模型调用，延迟和成本翻倍；
2. 单轮信息不完整，容易把一时气话写成事实；
3. 封存时能看到整段对话，判断“什么值得记”更准。

状态机：`open → waiting_handoff → sealed`。封存在后台生成摘要与记忆，发送方等窗口期满，最长 180 秒。

### 4.3 召回为什么不是纯 agentic

纯 agentic RAG 的问题是延迟与不稳定：模型想搜什么就搜什么，通常 3–5 轮工具调用，每轮一次 LLM 往返，几秒能变几十秒，同样的问题每次结果也可能不同。

所以把“检索”从模型手里拿走：

1. **程序预检索**：用当前输入（过短时拼上最近 3 条对话）并行查两个通道，固定给模型 3–6 张候选；
2. **缓存重放**：把最近读过、最近更新的卡片补进候选；
3. **模型只做判断**：选哪几张，或判定不需要记忆直接交卷。

模型可用四个工具：`search_memories`、`read_memories`、`list_memories`、`finish_selection`。补搜是允许的，但实测发生得很少——数据见[实验记录的“召回是怎么工作的”](<experimental records.md>)。

### 4.4 预检索的两个通道

- **grep 通道**：字面词命中，按命中次数排序。用户提到具体旧对象名时最准；
- **semantic 通道**：向量检索，取 limit × 2 个候选。

合并去重（同一篇两边都命中则 `matched_by` 有两个），排序键：

```
命中通道数 → grep 次数 → 向量名次 → 时间 → document_id
```

最后按 kind 截断：daily 3 张、topic 3 张。

### 4.5 时间为什么只能排第四

排前面会让“最近”压倒“最相关”：用户问一个月前的项目细节，召回却是昨天的闲聊。

但也不能去掉：同分情况下新记忆通常更准（同一个项目的当前状态比三个月前的旧状态有用）。所以它作为**平局裁决**，不作主排序键。

### 4.6 中文 grep 是个现实缺口

当前 grep 只认英文 token（`[A-Za-z][A-Za-z0-9_+#.-]{1,39}`）和用户显式打的引号短语，**不做中文分词，也不猜中文关键词**。

原因：没有可靠的轻量中文分词，与其瞎猜把无关记忆顶上来，不如让语义通道兜底。代价是中英混杂查询（“把 RAG 那个项目的检索再调一下”）只有 RAG 能被 grep 吃到。

改进方向：jieba + 停用词，并且用记忆库里的实体名做自定义词典，而不是通用分词表。

### 4.7 缓存重放

把前几轮读过、或最近刚更新的卡片正文直接带进候选，与预检索去重，数量有上限。

两个理由：**连续几轮聊同一件事时重复检索是浪费**；**最近更新的记忆能补上预检索看不到最新状态的问题**。

它只是候选，不是结论，最终仍由模型判断用不用。被选中卡片的来源占比见[实验记录的“选中卡片从哪里来”](<experimental records.md>)。

### 4.8 衰减与冷热分层

新鲜度分低于阈值即出热池。热池是检索主战场，冷池仍在库里但不参与默认召回。

不衰减的后果：三个月前的情绪记忆与昨天的平起平坐，而角色对“现在的你”应该更敏感。

回放时必须按**虚拟日期**推进降池（每段开始前调一次 retention 接口），否则用真实的“今天”去降历史数据，测出来的全是错的。

### 4.9 冲突与版本

- object：同一属性只保留最新值，带 revision 与 current_state，旧值进历史；
- topic：文档内有“当前状态”分区，必须引用最新条目；结构校验会验证这一点；
- daily：不覆盖，按天流水，冲突由 topic 层收敛。

每条记忆都带来源引用（source_refs），能回溯到具体消息——记忆写错时是可查的，不是玄学。

## 5. 上下文压缩与会话交接

### 5.1 为什么必须摘要

1. 成本随长度线性上涨，一轮塞 10 万字不现实；
2. 长上下文稀释注意力，角色在超长上下文里更容易失焦；
3. 长期陪伴注定分段，分段就必须有交接。

架构是三者互补：**当前窗口 + 上一段摘要（继承上文）+ 长期记忆**。

### 5.2 结构化摘要的约束

摘要不是自由发挥，是带分区与引用的结构化输出：身份、关系、事件、约定、情绪基调；每条结论必须指向具体消息。

几个必须写死的约束：

- 每条约定必须带 `decided_on`（哪天定的），并且按消息的**当地日期**判断，不能用 UTC；
- 超预算即判重写，重试 1 次；
- 输出必须正常结束（`finish_reason` 为 stop），被截断的摘要直接拒用——**截断摘要比没有摘要更危险**；
- 结构层自动校验：来源引用是否存在、日期是否一致。

摘要一定有损。它的定位是“给下一段一个像样的开场”，不是完整存档。

### 5.3 生成不等于消费（踩过的坑）

交接摘要生成后要进入**下一段会话的提示词**才算数。早期回放脚本每段新建对话，摘要 100% 生成了，却 0% 被读到——功能是通的，产品是断的。改成全程复用同一对话、封存后接后继会话，继承才真正生效。**评估时必须把“生成”和“消费”分开测。**

### 5.4 失败要能降级

分两层兜底：

1. 重试：超预算自动重写一次；
2. 降级交接：仍失败则不要摘要，直接用最后一轮之后的原始对话做交接（tail 窗口），会话照常往下走。

含义：**宁可没有摘要，也不能让角色卡在“等待交接”里不动**——用户看到的是“发消息没反应”，这是最差的产品体验。

代价是丢掉上一段的压缩结果，但最近原始对话还在，短期连续性够用；长期信息仍在 daily / topic 里。

## 6. 评估体系

单测只能保证不崩溃。提示词改一句，输出整体偏移，但没有任何断言会失败——所以需要一套用真实历史对话重放的评估。

### 6.1 回放要解决的三件事

1. **可复现**：同一份输入能反复跑，才能做 A/B；
2. **可追溯**：每轮的召回结果、**真正注入提示词的记忆原文**、回复、耗时都要落盘，指标不对时能回看具体轮次；
3. **不测偏**：时间轴、冷热、封存都要按虚拟时间走，否则测的是脚本自身的行为。

### 6.2 六个步骤

1. 读表格：按 session 分组、按 created_at 排序，得到段与轮；
2. 平移时间轴：整份日志平移到最近，保持原始间隔与时分秒；
3. 逐段重放：发消息 → 等回复 → 段末把消息时间改写为虚拟时间 → 封存 → 等记忆生产；
4. 复用同一个对话：封存会把会话换成后继会话，下一段接着用——否则继承上文永远是 0；
5. 按虚拟日期降池：每段开始前调一次 retention 接口；
6. 每轮写完立即 flush，中断不丢已完成轮次。

具体命令、参数、产物格式见 [replay-guide](../backend/scripts/replay-guide.md)。

### 6.3 分层指标

不报准确率——这类任务没有唯一正确答案，硬算只会自欺。按链路拆成四层，每层都能追溯到具体轮次：

| 层 | 问的问题 | 指标 |
|---|---|---|
| 要不要召回 | 该不该给记忆 | 弃权率、弃权正确率 |
| 召回到什么 | 选中的卡片对不对 | topic 选择命中率、topic 覆盖率 |
| 用没用上 | 记忆有没有起作用 | 记忆落地率 |
| 稳不稳定 | 工程指标 | 延迟、token、结构合规 |

各指标的定义、口径陷阱（比如多选会虚高）、以及两轮实验的实测数字，全部在[实验记录](<experimental records.md>)里，此处不重复。

### 6.4 一条方法论：指标要先验伪

评估最贵的一课不是“怎么测”，而是“测错了会怎样”。有三类指标算起来很顺、结果也很规整，结论却完全是错的：

| 指标 | 想测什么 | 为什么不行 |
|---|---|---|
| 卡片 ID 交并集 | 是否重复注入同一份记忆 | ID 不承载语义，集合相同的轮次正文相似度只有 0.32 |
| daily 与当前轮的日期距离 | 召回的 daily 是否过时 | 旧不等于不相关，间隔超过 7 天和 7 天以内的线索率几乎一样 |
| 相邻两轮输入的 2-gram 相似度 | 是否换话题 | 中文短句字面重合极低（中位 0.014），“培训项目”和“桌宠”字面零重合却直接相关 |

共同点：**拿结构化字段或字面特征去推语义相关性**。

现在定下的规矩：任何新指标先拿 20 条样本人工对一遍，对不上就废掉。

## 7. 工程与成本

### 7.1 成本

单轮成本由三块构成：召回判断一次、生成一次、封存时摘要与记忆生产的摊销。具体金额与提示词 token 构成见[实验记录的“稳固人设”](<experimental records.md>)。

可压缩的点：

1. 召回判断换小模型（选择本质是分类任务，不需要主力模型）；
2. 记忆生产走批处理，同一段只调一次；
3. 固定部分（角色卡 + 示例）走 prompt caching。

### 7.2 延迟瓶颈在哪

向量检索是毫秒级，预检索整体 < 300ms；**绝大部分时间花在那一次 LLM 判断上**。实测分位见[实验记录](<experimental records.md>)。

优化排序：换小模型 > 并行/流式 > 单候选直接跳过判断 > 缓存。

### 7.3 多用户的改造点

现在的假设是本地单用户。改服务端需先解决：

1. 记忆按 character + user 隔离（当前只按 character）；
2. Qdrant 从本地模式换服务模式，加 collection 分区；
3. 封存任务从进程内异步改成队列（当前失败会停在中间状态）。

### 7.4 隐私

全本地：模型走自己的 key、数据在本地 SQLite 与 Qdrant、无云端账号。这类产品用户说的话很私密，能本地就本地。

## 8. 可复用的经验

**1. 指标选错比不测更糟。** 有些指标算得很顺、结果好看，结论全错。先拿 20 条样本人工对一遍再信它。

**2. 生成和消费要分开测。** 摘要生成了但没人读，功能通、产品断。凡是“生成 → 注入 → 被用”的链路，至少要有三个断点检查。

**3. 延迟的大头通常在判断，不在检索。** 优化索引之前先把链路拆开量一遍。

**4. “多选”类指标天然虚高。** 一次给三个候选，命中率必然接近 100%。凡是指标允许“多选命中”，就要单独报单选口径。

**5. 时间只能做平局裁决。** 时序特征很强，但一旦提到主排序，就会压倒相关性。

**6. 降级路径比完美实现更重要。** 任何长链路都要先想清楚“失败了用户看到什么”。

**7. 评估要前置。** 先做功能再补评估，中间会积累大量“改了不知道好坏”的改动。

**8. 报数要说清口径。** 全部 vs 抽样、单选 vs 多选、生成侧 vs 消费侧——同一个结论换口径能差三倍。

## 9. 已知缺陷

1. **召回偏多**：放弃侧的判断是准的，但门槛太低，倾向“宁滥勿缺”；实测见[实验记录的“召回克制”](<experimental records.md>)。
2. **中文检索缺位**：grep 对中文基本无效，等于少一个通道。
3. **交接失败无人接管**：封存已返回“等待交接”而任务随后失败时，会话会停在中间状态；现有兜底是等待 + 降级交接，缺独立的清理任务。
4. **单用户假设**：记忆只按 character 隔离，改服务端要先动数据模型。
