### 每个指标量的是什么

| 指标                          | 量的是什么                                                   | 怎么读                                 |
| ----------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 系统对话数 / 会话数           | 脚本建了几个对话、封存出几个会话；一次封存换一个会话         | 结构指标，不反映效果                   |
| 记忆召回触发                  | `recall_status=ready` 的轮次，即真的把记忆正文注入了提示词   | 不是"召回率"——该不该召回没有唯一答案   |
| 主动放弃占比                  | 库非空之后，模型以 `context_sufficient` 交卷、一张卡片都不选的比例 | 只看行为，对错要人工标注才知道         |
| 弃权正确率                    | 主动放弃的轮次里，人工判定"确实该放弃"的比例                 | 越高越好；这一项两轮都是 100%          |
| topic 选择命中率              | 选中了 topic 的轮次里，该 topic 与这轮对话主题一致的比例     | 多选几乎必中，要看单选（85%）          |
| 平均注入记忆文档              | 每轮选中的正式记忆文档数，同轮内去重                         | 少而准优于多而全                       |
| 每次召回工具调用              | 预检索算 1 次，超出的部分是模型自己补搜                      | 低省往返，但补搜多也可能是预检索不够   |
| 召回延迟                      | 端到端口径，含一次 Agent 决策                                | 不是向量检索耗时                       |
| 提示词 token 中位             | 整份 prompt：固定内容 + 记忆 + 摘要 + 历史 + 当前输入        | 涨得最多的通常是摘要与历史             |
| 提示词里带继承上文            | 本轮 prompt 里是否含上一会话的交接摘要                       | 量"带没带上"，不量"用没用上"           |
| 继承上文被回复用到            | 人工判定回复是否依赖只有摘要里才有的信息                     | 抽样推算，不是全量                     |
| 记忆正文块数                  | 注入的正文块数，已剔除时间轴伪影                             | 块数看体量，字数看密度                 |
| 含称呼的记忆块 / 回复含称呼   | 覆盖率，同上                                                 | 也许能用来衡量人设漂移，实际需要看体感 |
| 回复长度中位                  | 字符数                                                       | 太短像敷衍，太长会失焦，没有标准值     |
| 记忆落地率                    | 回复里出现注入记忆专有信息的比例                             | 需要人工抽查                           |
| topic 主题 / 条目 / 引用      | 合并后的事件档案件数 / 条目行数 / 带来源引用的条目数         | 条目多而引用齐，说明拆分干净           |
| 记忆生产任务                  | 封存后触发的记忆生成任务数                                   | 与段数同量级                           |
| 记忆库 daily / object / topic | 最终库里的文档数                                             | 看分层是否均衡，不看总数               |
| 回复截断                      | 句子没写完被判截断的回复数                                   | 越低越好                               |

**"注入记忆文档"怎么数。** 一个被选中的正式记忆文档算一张：daily 是某一天的日记（id 形如 `daily:character_deepseek:2026-09-29`），topic 是一个持续事件的完整档案（id 是 UUID）。同一轮里同一个文档只计一次。分布是 1 张 8%、2 张 26%、3 张 29%、4 张 24%、5 张 11%、6 张 2%——不是被截断的，上限 `final_doc_limit` 是 10，这份日志最多只用到 6。

### 继承上文的实际作用

**202 这个数是哪来的。** 实验 B 的 273 轮里有 202 轮，提示词里真的带上了上一段的交接摘要（实验 A 是 0 轮）。没有带上文的轮次里，这题根本无从谈起，所以抽样池就是这 202 轮。

在这 202 轮里随机抽 24 轮，按"这轮回复靠什么接上话"分类：

| 靠什么接上                     | 抽样    | 占 24 轮 |
| ------------------------------ | ------- | -------- |
| **继承上文**                   | 6 / 24  | 25%      |
| **长期记忆**                   | 7 / 24  | 29%      |
| 都不需要（纯接话、玩笑、复述） | 11 / 24 | 46%      |

把"都不需要"的 11 轮去掉，剩下 13 轮真正靠历史接话：**继承上文 6 轮（46%）、长期记忆 7 轮（54%）**——两者差不多各占一半。

**继承上文和长期记忆在信息上高度重叠，拿掉继承对回复的影响其实很小**——这也解释了为什么 A/B 两轮里除继承相关指标外其余几乎没差别。

继承上文的真正价值不在"提供事实"，而在**当前窗口内的措辞、情绪和没聊完的线索**——这些长期记忆模块不会记。

## 稳固人设：提示词构成

以实验B为例，提示词是按固定顺序拼起来的（`PromptBuilder.build()`），占比按 273 轮的总字符算（合计 1826288 字，约 1.74 字/token）：

| 顺序 | 部分       | 占比      | 累计  | 内容                                     |
| ---- | ---------- | --------- | ----- | ---------------------------------------- |
| 1    | 系统提示词 | 6.4%      | 6.4%  | 身份约束、输出 JSON 协议                 |
| 2    | **角色卡** | **41.8%** | 48.2% | 身份、品格、关系立场、语言指纹、视觉表达 |
| 3    | 上下文规则 | 1.5%      | 49.7% | 记忆与总结不是用户发言、不编造共同经历   |
| 4    | 固定示例   | 15.2%     | 64.9% | 6 组成对的 user/assistant 示范           |
| 5    | 注入记忆   | 7.3%      | 72.1% | 本轮召回总结（217 / 273 轮有）           |
| 6    | 历史摘要   | 13.1%     | 85.2% | 上一会话交接摘要                         |
| 7    | 历史对话   | 11.8%     | 97.0% | 当前窗口内已完成的轮次                   |
| 8    | 本轮锚点   | 2.3%      | 99.3% | 贴着当前输入的最后一道行为约束           |
| 9    | 当前输入   | 0.6%      | 99.9% | 这一次用户说的话                         |
| 10   | 场景示例   | 0.0%      | 99.9% | 相似情境的表达参考（本次未启用）         |

- **前四段（1–4）全是固定内容，占 64.9%**，每轮一字不改地重复。人设的表达主要靠这一块撑着。
- **注入的记忆只占 7.3%，不到固定示例的一半。** 所以调记忆很难压过角色卡定下的基调——这也是"人设漂移"要靠改角色设定、而不是靠少召回记忆来解决的原因。

这是本项目的固定参数。如果要增大上下文窗口，可以在 env 里调 `RNA_CONTEXT_SESSION_TARGET_TOKENS` 等三项；暂未实测扩大多少会造成漂移。**本次测试未发现明显的角色漂移（人工回看对话）。**

## 记忆筛选：

### 召回是怎么工作的

一轮召回由三段组成，不是模型自己去搜：

1、**程序预检索**：用当轮用户输入做查询（输入过短时拼上最近 3 条对话），在热池检索。daily 与 topic 各取前 3 张，**合计最多 6 张**，每张带正式原文——daily 是五个公开分区全文，topic 是身份边界与当前状态。

```
预检索 query → 两个通道并行
   ├─ grep 通道：字面词命中，按命中次数排
   └─ semantic 通道：向量检索，取 limit × 2 个候选
        ↓
     合并去重（同一篇两边都命中则 matched_by 有两个）
        ↓
     排序：通道数 → grep 次数 → 向量名次 → 时间 → id
        ↓
     按 kind 配额截断（daily 3 张、topic 3 张）
```

2、**缓存重放**：`RECENT_RETRIEVALS` 会带上前几轮读过、近期更新的卡片正文（最多 5 张近期更新 + 10 张最近已读），与预检索结果去重后一起给模型。近期更新可以弥补预检索带来的最新状态不足的问题。

3、**模型判断**：决定选哪几张、或判定无需历史直接 `context_sufficient` 交卷；不够时可以再调 `search_memories`。

所以"平均 0.99 次工具调用"里的那 1 次，**就是预检索本身**。253 次召回中，模型自己额外补搜的只有 **16 次（6%）**，预算 8 次调用、实际中位 0 次、最多 1 次。省掉模型多轮搜索的往返，是召回延迟能压到 P50 8.2s 的原因。

**补搜的触发点很集中**：用户提到一个具体旧对象、而预检索只命中了泛泛的相似内容。补搜时把 `limit` 从 3 提到 6–10，**要的是精度不是广度**。

### 选中卡片从哪里来

被选中的卡片按来源分（按 `read_handle` 的注册顺序推断）：

| 来源                     | 占比    |
| ------------------------ | ------- |
| 本轮预检索               | 23%     |
| 近期更新的正式记忆       | 15%     |
| 本轮之前已读（缓存重放） | **62%** |

这是对话连续性的自然结果——连着几轮聊同一件事，复用上一轮读过的记忆是对的。**它也解释了补搜率为什么只有 6%：不是预检索足够，是模型往往不需要新检索。**

### daily 与 topic 的分工

**记忆在这里的主要作用不是提供最新事实，是提供背景和情感连续性。** 背景由 topic 提供，情绪由 daily 和当前对话、以及模型本身能力提供（daily 由模型带入第一人称视角写）。

实测没有出现"用了过时 daily"的情况：

- 按"当时已存在的 daily 里，有没有更新且与本轮更匹配的候选"筛选，219 轮中有 54 轮（25%）存在这样的候选，但**匹配度全部低于 0.5**（多在 0.03–0.13，毕竟一篇 daily 很长，相似度肯定被压得很低），与已选中的几乎持平。语义相似度在这个量级上区分不开新旧。
- 更根本的原因是 **daily 不是"一个话题一条"，是同一天一条**：同话题的几天日记会同时出现在候选里，模型可以挑，不是二选一。

注：哪怕召回的情感是错的，或者没有召回回来对应的情感，还有记忆总结模型的独立判断和输出情感，会压制住错误的情感输出。

### 背景有没有选对

topic 是这套记忆的重点：daily 给情绪和细节，**背景事实主要由 topic 提供**，topic 选错比没选更糟——模型会拿一整段不相干的往事来垫（即答非所问）。所以这一项单独判。逐条判"选中的 topic 和这轮对话对不对得上"：

|                           | A                            | B                            |
| ------------------------- | ---------------------------- | ---------------------------- |
| 带 topic 的召回轮次       | 176 / 221（80%）             | 143 / 217（66%）             |
| 命中（至少一个 topic 对） | **160（90.9%）**             | **126（88.1%）**             |
| 其中单选                  | 113 次，命中 97（**85.8%**） | 105 次，命中 89（**84.8%**） |
| 其中多选                  | 63 次，命中 63（100%）       | 38 次，命中 37（97.4%）      |

**多选的 100% 是虚的。** 一次带两三个 topic，几乎总能蒙中一个——真正要看的是单选：**85%**。

**错法很一致：把生活里的小事往topic上靠。**也就是说，**遇到情绪、生活、新计划这类话题，它倾向于抓最近聊过的topic**，这也能理解，模型需要抓最近聊过的东西来判断用户是不是因为这件事而产生的话题。反过来，只要用户明确在聊某个topic，topic 没选错过——90% 的命中率基本来自这一半。

反过来看另一半：**召回了、但一张 topic 都没带**的轮次（A 45、B 74），只有 daily 在接话。这些逐条判"是不是该带"。

|                                  | A            | B             |
| -------------------------------- | ------------ | ------------- |
| 无 topic 的召回轮次              | 45           | 74            |
| 其中 topic 还没生成（不算漏）    | 21           | 20            |
| 真正在候选里的                   | 24           | 54            |
| **该带没带**                     | **6（25%）** | **22（41%）** |
| 本来就不需要（情绪、道别、状态） | 18           | 32            |

把两头合起来算**覆盖**——命中 ÷（命中 + 该带没带）：

|      | 命中 | 该带没带 | 覆盖      |
| ---- | ---- | -------- | --------- |
| A    | 160  | 6        | **96.4%** |
| B    | 126  | 22       | **85.1%** |

**A 的 topic 覆盖反而更高，差距全在"漏带"上，不在"带错"上。** A 带 topic 的召回占 80%，B 只占 66%。一个可能的原因：B 有继承上文垫背景，模型更少去要 topic；A 没有上文，只能靠记忆补，反而把 topic 要得更勤。

### 召回克制

这个记忆选择agent的另一个特点是主要选择不带入记忆。这类聊天系统真正难看的不是"没召回到"，是"不需要也硬塞一段往事"造成噪声。所以召回 Agent 有一条明确的放弃路径：没有需要历史补充的目标时，直接以 `context_sufficient` 提交，不选任何记忆。

- **弃权率 14%**：B 的 253 轮里 36 轮主动放弃，A 的 252 轮里 31 轮。
- **弃权正确率 100%**：67 次放弃（A 31、B 36）逐条看完，全部判对——道别、网络故障、纯玩梗、当前状态陈述，没有一次该召回却放弃。**放弃这一侧是可以信的。**
- **召回贡献率约三分之一**：随机抽 3 组、每组 30 轮，回复里能追到注入记忆内容的比例 A 37%、B 29%。其余约三分之二的召回只在读，没在回复里显形——多数是背景，不是素材。

| 抽样    | A 回复用到记忆     | B 回复用到记忆     |
| ------- | ------------------ | ------------------ |
| 第 1 组 | 14 / 30            | 9 / 30             |
| 第 2 组 | 10 / 30            | 7 / 30             |
| 第 3 组 | 9 / 30             | 10 / 30            |
| 合并    | **33 / 90（37%）** | **26 / 90（29%）** |

**召回其实有两道关口，第二道常被忽略。** 术语上分"选择阶段"和"总结阶段"：前者决定选中哪些卡片，后者决定本轮真正注入什么。

| 层       | 结果                 | 轮次      | 占比 |
| -------- | -------------------- | --------- | ---- |
| 选择阶段 | 主动放弃             | 36 / 253  | 14%  |
| 总结阶段 | 选中但判空           | 1 / 217   | 0.5% |
| —        | 召回了但回复里没留痕 | 154 / 217 | 71%  |


## 记忆正文长度

空壳和退化可以直接看出来，记一下实验 B 注入原文的长度（已剔除回放伪影）：

| 分位 | P0   | P5   | P25  | P50  | P75  | P90  | P100 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 字数 | 10   | 264  | 461  | 561  | 702  | 833  | 1180 |

平均 573 字。P5 已有 264 字，说明最差的情况也给出了实质内容；≤30 字的只有那 1 例判空。

> **剔除的伪影是什么。** 召回与总结发生在对话过程中，读到的是消息入库时的真实时间；回放改写消息时间是在段末做的，两者对不上，于是部分正文里出现了回放运行当天的真实日期。这是回放的时间轴伪影，真实使用不存在，统计记忆正文时把它们剔掉（217 → 172 块）。剔除前后差异很小。

## 局限

- 实验B中**有 1 段的数据是断的。** 27 段里 1 段摘要超出 token 上限，封存没能交出后继会话，脚本换了新对话继续——这一段的继承上文因此缺一段，其余指标从后继会话重新起算。
- **同一份输入两次回放，输出不完全相同**（回复是现生成的）。适合做 A/B 对比，不适合当固定基准。
- **没有人工标注的正确答案集**，所以不报准确率。
- **语义质量只能人读。**"同一天的几条记忆该不该合并""总结有没有漏掉关键信息""一次性行为有没有被记成约定"，这些规则筛不准——用关键词判断"否定是否保留"，误报接近 100%。
- **时间轴只对记忆侧和封存侧生效。** 回放改写消息时间是在段末做的，而召回与总结发生在对话过程中，读到的是消息入库时的真实时间——它们从 `CHAT_CONTEXT.created_at` 推断"今天"。所以记忆文档的 `memory_date` / `acquire_time` 是虚拟的，召回总结正文里的日期是真实的；交接摘要在改写之后运行，是虚拟的。按日期做统计分析时不能混用。
