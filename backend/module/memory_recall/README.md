# 记忆召回

大部分的聊天ai采用的是根据上下对话原文直接检索召回的方式来获取相关记忆，优点是保障了模型的整体对话的回复速度，缺点是召回的质量得不到保证（一方面是没有明确的召回开关，无论当前需不需要记忆都会召回，能不能排除噪声取决于回复模型的能力，一方面是对话原文本身是包含很多噪声的，因此靠混合检索保证不了召回的质量）。记忆整理只是负责更好的整理（写）好长期记忆内容，召回就是读，写决定了下限，读决定上限，这里选择牺牲回复速度来保证召回的准确度。

记忆召回在角色回复前，根据当前输入和对话上下文，寻找可能有帮助的长期记忆。采用了 Skill 式编写的工作流程，并用程序实现循环，让模型决定是否查找、查看哪些材料以及何时结束，再将选中的材料整理为回复所需的记忆总结。

## 整体功能

| 功能 | 作用 |
| --- | --- |
| 记忆选择 | 根据当前对话判断是否需要历史，通过工具逐步寻找和选择材料。 |
| 跨轮复用 | 复用近期更新和读取过的记忆，并根据更新信号刷新。 |
| 记忆总结 | 将本次选中的材料整理为与当前对话相关的文本，供回复生成使用。 |

## 设计特点

### 记忆选择agent：先判断目标，再决定是否继续查找

普通相似度检索可以快速找出语义接近的片段，但它只能说明“文本相似”，不能单独确定用户说的是哪次经历、目前处于哪个阶段。本模块让选择模型结合当前输入、近期对话和已展示的材料逐步判断；程序负责执行工具、验证权限和控制预算。这样回复模型拿到的是经过一轮选择的材料，而不只是搜索结果的前几名。

一次选择大致经历以下循环：

1. **准备材料。** 将当前输入、近期对话、角色关系边界、近期更新与已读记忆、可用范围和预算交给模型。默认还会根据当前输入和近期真实对话先执行一次预检索，不需要额外调用模型生成搜索词。
2. **判断是否有明确的历史目标。** 模型先依据当前对话确定要找的事件、人物、经历或话题；没有需要历史补充的目标，或只有无法确定所指的代词时，应直接结束，不能从搜索结果反过来猜用户的意思。
3. **检查已有材料与缺口。** 有目标时，先看预检索和近期材料：可见正文足够就提交；已定位候选但缺细节就读取；尚未定位且有具体线索时才进一步搜索。每次调用后，程序把结果回填给模型，再判断是否需要下一步。
4. **核对并提交。** 模型通过 `finish_selection` 提交结束原因和选中的正文分区；程序检查句柄、可见范围、重复分区与预算。校验通过后，从本轮固定的已读材料提取正文；不通过时在剩余额度内要求修正。

这里的“按需”是指模型按当前目标决定继续查找和采用什么，**不意味着每次都不检索**：预检索默认开启，即使模型之后判断无需历史，也可能已经进行了一次搜索；它会计入工具和时间预算，也可以配置关闭。

**检索范围分热池与冷池。** 每条 daily / topic 记忆都带 `recall_tier`：`hot` 默认参与检索，`cold` 需要显式回捞。记忆长期未被提及后按半衰期 7 天的衰减分数降入冷池（低于 `0.1` 时降池，约 23 天）；降池只改变检索范围，不删除证据。判据与启动时的降池检查见 [记忆管理文档](../memory_management/README.md#召回池热池与冷池)。

| 工具 | 判断条件 | 作用 |
| --- | --- | --- |
| `search_memories` | 有明确目标和具体线索，现有材料仍不足 | 在热池按字面、语义或组合方式寻找候选。 |
| `read_memories` | 已找到可能相关的卡片，但展示内容不够 | 读取本轮已展示卡片的正文，再选择需要的分区。 |
| `list_memories` | 需要某段时间的事件概览，或符合历史回忆的最后查找条件 | 概览查热池。冷池回捞要求本轮已执行热池搜索且有明确历史线索。 |
| `finish_selection` | 材料足够、无需记忆、查找结束或存在无法完成的缺口 | 单独提交选择、结束原因及必要的未解决问题。 |

### 近期材料可以缓存，也会跟随更新

连续聊天可能反复提到同一件事。系统在会话中复用近期检索正文和近期更新记忆，供下一次选择参考，减少重复查找；发生更新或删除时，会根据信号重新核对正式版本。缓存保存的是正文与版本信息，新一轮重新签发自己的句柄，避免把上一次选择的临时句柄当成永久权限。

### 选择记忆卡片 -> 模型带入角色总结记忆

记忆选择 Agent 找到的是与当前对话有关的日记和主题分区，但一份相关记忆仍可能包含暂时用不上的内容，多份记忆也可能重复描述同一件事。如果直接把卡片堆给回复模型，回复模型还需要一边筛选历史、一边理解角色和生成回答，容易受到无关细节干扰。

因此，选择完成后，系统让总结模型结合**当前输入、近期对话、选中的记忆及角色设定**，再次围绕本轮话语整理材料。选择循环解决“找哪些材料”的问题；总结解决“这些材料中，什么值得角色在这一刻想起来”的问题。前面的选择方式未来可以根据速度和效果调整，例如探索更精细的程序性召回；角色视角的总结则承担将材料转换为本轮可用回忆的职责。

| 整理方向 | 如何处理 | 希望达到的效果 |
| --- | --- | --- |
| 事件发展 | 优先从相关主题中梳理关键进展和截至已知时间的状态，必要时用日记补充当时经历与感受。 | 让角色理解事情从哪里发展到哪里，不把旧计划误当成最新结果。 |
| 对用户的意义 | 保留用户明确表达过的期待、担忧、投入和取舍；有依据的理解保留其不确定程度。 | 让角色理解事情为什么对用户重要，而不只复述事件清单。 |
| 相关经历 | 只在有具体共同处境、且能增加理解时简要补充此前经历。 | 提供有用背景，避免因为关键词或情绪相似就硬套旧事。 |

总结的产物是留给回复阶段的记忆文本，**不是替角色提前写好回复**：总结模型不输出台词、动作或回复建议。卡片正文是证据层的第三人称记录，总结时要把“用户”“他”换成角色平日对这位用户的称呼（由角色的 user_appellation 注入，缺省为“你”），只换称谓，不改事实和时间。没有选中记忆时跳过总结；若总结失败或未完成，系统保留选择结果并标记状态，不把它冒充为成功的总结。

带入角色视角的记忆总结相对于是提前整理好了回复思路，模型在这些回复思路中选择一条用到回复当中，否则只是召回了相关记忆卡片，回复模型根本不知道用哪个，最后就只是费时费力召回了，但是没用上。



### 在准确性与响应时间之间设预算

在每次循环过程中，将剩余耗时也一并发给模型能有效减少耗时，但是不能保证模型一定会在指定耗时内返回，因此这里的耗时限制只是一种督促的设计。经测试，一搜+一读+总结的耗时稳定<10s，如果是进行深度的记忆查找，不会超过20s（系统强制收尾）。

多轮选择和总结会增加回复前的等待，因此系统不要求把所有候选都读完：摘要足够即可提交，有明确缺口才继续，最近用过的材料可以复用。默认预算如下，可随配置调整：

| 限制 | 默认值 | 用途 |
| --- | --- | --- |
| 选择模型调用 | 最多 6 次 | 限制“判断—调用—再判断”的循环长度。 |
| 工具总调用 | 最多 8 次，包含最终提交 | 搜索最多 2 次、读取最多 2 次、列举最多 1 次，并为提交保留额度；预检索也计数。 |
| 工具返回材料 | 12000 token | 限制工具回填的材料量，避免上下文无限膨胀。 |
| 最终选择 | 最多 10 篇、48000 token | 限制送入总结阶段的文档数和材料量；单篇正文另有4000 token 上限。 |
| 选择时间 | 软目标 10 秒，硬保护默认 20 秒 | 接近目标时催促提交；达到硬保护时终止等待并标记未完成。 |
| 选择与总结总时间 | 总结目标 11 秒，整体软限 12 秒，硬保护默认 24 秒 | 选择和总结共用时间窗口；软目标不是立即取消请求的硬超时。 |

材料预算将对应数据序列化为 JSON，再使用本地 DeepSeek tokenizer 计数；它不包含完整模型请求的消息模板和工具协议开销，也不代表其他模型的实际计费。时间为默认配置下的目标和保护边界，不代表实际响应时间承诺；模型、网络、数据量和配置都会影响耗时。

系统还通过几种方式减少不必要的等待：预检索在首次选择模型请求前准备候选；近期正文经更新信号核对后可直接复用；没有选择任何记忆时跳过总结。接近选择目标、模型调用次数见底、工具额度接近耗尽或提交曾被拒绝时，循环转入只提交阶段，不再继续发起读取工具。

如果模型或工具失败、预算耗尽，系统区分“正常查找但没有相关记忆”和“必要查找未完成”；未经有效提交的预读结果不会自动被当成成功选择。输入有效性发生变化时，旧尝试会被取消。总结失败时保留选择结果并标记未完成，而不是声称已经生成可靠总结。
