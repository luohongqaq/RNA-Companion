# 记忆管理

记忆管理将已经封存的对话转化为可长期使用的结构化记忆。它在后台处理会话，保存正式数据并建立检索索引，供记忆召回使用。

## 功能

| 功能 | 作用 | 处理方式 |
| --- | --- | --- |
| 日记（daily） | 按日期整理对话中的记忆 | 对封存会话按日期分组，发布记忆文档并建立索引，供后续召回 |
| 事件提取（object） | 提取一件事情的进展、计划和来源 | 按会话提取并校验事件对象，建立索引后激活 |
| 主题整合（topic） | 将对象和相关材料整理为主题记忆 | 等待对象提取完成，检索相关对象和主题，生成、发布并索引主题 |
| 留存（retention） | 控制记忆默认参与检索的范围 | 按半衰期衰减分数把长期未被提及的记忆从热池降入冷池；降池不删除证据 |

长期记忆的整理分为三个环节，结合了检索增强生成（RAG）和关联组织的思路，服务于持续聊天。单纯依靠相似度检索时，即使找到了相似的对话，也不一定能分清它描述的是哪一次事件、处于什么阶段；显式知识图谱能表达关联，但需要持续维护实体与关系，错误关联也可能影响后续推理。这里保留原有对话的语境，同时将反复讨论的同一件事整理成有边界、有时间线的主题，让检索有更多可辨认的材料。

## 设计特点

记忆既要让角色想起当时发生了什么，也要帮助它理解一件事后来有什么变化。下面的设计围绕这两个需求展开。

### 日记保留当时的记忆，主题记录事情的发展

daily 按日期保留角色与用户的经历和当时语境；topic 则围绕同一件持续发展的事，组织不同会话里的进展和当前状态。例如，多次聊到同一次求职时，每天的 daily 可以保留那天的经历与感受，topic 则可以把投递、面试和结果串成时间线。

根据目前的个人真实对话实践，topic 可以较好地把同一事件的进展串起来。对于只聊过一次的事，daily 仍可提供当时的上下文，不必为每次提及都建立独立主题。

### 日记供模型阅读，也供用户开放修改

日记并非只为向量检索准备的片段：它是一份有标题和明确栏目的记忆，既能为角色提供可阅读的上下文，也能让用户查看和修改。

**特点1**：由模型带入指定角色去整理日记，实验证明，写出来的更像真人日记，而不是流水账，并且带入角色后，会更加突出去记录重要的事，而非琐事。

**特点2：**重要经历、人物事实、意图、承诺和角色反思分开表达，模型和用户更容易区分“用户想做什么”“双方约定了什么”和“角色对此有什么看法”，也方便发现并纠正记错的内容。

**特点3：**开放性。这样做的目的是让记忆对用户可见、可理解、可干预，而不是让错误长期藏在不透明的摘要里。此外，用户去读角色第一视角写的日记也会更耐心去读和改，承诺和角色反思部分也能让用户感受到角色在对话之外体现的陪伴感。

### 从单次事件到跨会话主题

一次聊天只能看到一件事的局部，而长期陪伴需要知道这件事后来怎么样了。难点在于：用户不会每次都用相同的名字讲述，也可能同时谈论好几件相似的事。如果只把每次聊天各自存成摘要，相关进展就会散落在不同日期；如果仅凭关键词或相似度合并，又容易把不同事情混在一起。

这里的解决思路是**先留下每次谈话中的事件记录（object），再等后续对话提供线索，逐步判断哪些记录属于同一件持续发展的事**。系统不要求在第一次听到一件事时就给它确定一个永久主题：

1. **先记录，不急着归档。** 每次会话结束后，提取其中值得追踪的事件和计划，保留陈述及来源。暂时找不到归属的记录先留在暂存池，等待之后的新材料；单次谈话仍可以通过 daily 提供当时的语境。
2. **用新记录寻找过去的线索。** 当新的事件出现时，系统既寻找相似的暂存记录，也寻找可能相关的已有主题；已归入主题的记录还可以提供指向该主题的线索。这样，即使用户换了一种说法，仍有机会找到以前讨论过的事。
3. **相似只是线索，同一件事才合并。** 系统进一步判断事情的对象、范围和前后关系：投递简历、参加面试、收到结果，可能是同一次求职的不同阶段；另一场求职即使也涉及面试，也不应仅因措辞相近就合并。无法可靠判断时继续暂存，避免靠关联关系一路扩大主题。
4. **持续讨论后再建立主题。** 当前默认至少需要用户在三个不同会话中实质讨论同一件事，才能申请新建主题。三个会话不必恰好构成三个阶段：也可能是对同一件事的补充。已有主题则不必重新满足门槛，可以根据新的可靠记录继续更新。

例如，用户先说“准备换工作”，后来谈到“面试了两家公司”，再后来提到“接受了新 offer”。三次说法并不完全相同，但如果上下文表明它们属于同一次求职，就可以整理为一个主题：保留准备、面试和接受 offer 的过程，并把最新已知状态更新为已接受 offer。如果用户后来只是补充其中一场面试的细节，系统应补充原有记录，而不是凭空制造一场新面试；如果用户更正了先前的说法，也应保留更正关系。

这套设计的思想在于，**把“找得到”和“确定属于同一件事”分开**：检索负责扩大可比较的范围，归属判断负责守住事件边界；暂存和跨会话门槛则让主题从持续出现的讨论中逐渐形成，而不是预先为所有对话分类。主题因此既能串起分散的进展，也能保留原先的时间与依据。这个门槛也有取舍：只讨论过一两次的事可能不会成为独立主题，会设计遗忘因子，最后根据时间线的推断而归档，object库不会持续膨胀。

由于不能保证完全正确（没有微调小模型去做专门的工作），如果用户愿意，用户是可以手动去修改topic的。

### 召回池：热池与冷池

记忆不是永远全量参与检索。每条 daily / topic 记忆带一个 `recall_tier`，取值来自 `module.shared.memory.types.retention.RecallTier`：

| 池 | 是否默认参与召回 | 如何进入 |
| --- | --- | --- |
| 热池（`hot`） | 是 | 新产生的记忆默认落在热池 |
| 冷池（`cold`） | 否，需要时显式回捞 | 长期未被提及，衰减分数低于阈值后降池 |

> `RecallTier` 还定义了 `archived`，数据库约束也允许该值，但当前没有代码路径会写入它；归档行为目前由 object 的 `forgetfulness` 标记和主题门槛共同表达，而不是靠这个池。

判据是半衰期 7 天的衰减分数（`retention/core/processing/service.py`）：

```python
score = 0.5 ** (elapsed_days / HALF_LIFE_DAYS)   # HALF_LIFE_DAYS = 7
tier = RecallTier.HOT if score >= HOT_THRESHOLD else RecallTier.COLD   # HOT_THRESHOLD = 0.1
```

即约 23 天没有被提及的记忆会离开默认检索范围。

`MemoryRetentionService.cool_expired_memories` 在应用启动时执行一次：先遍历当前热池记忆重算分数，**先把池状态同步到向量索引、再提交正式池状态**；如果某条记忆在索引里找不到对应分区，就暂缓降池并记录告警，避免数据库和索引不一致。因此热池检索本身就是"默认范围"，查询时不需要额外过滤条件。

**降池只改变检索范围，不删除任何证据。** 正文、来源引用和修订记录都保留，冷池记忆在需要时仍能被找回（召回侧的回捞条件见 [记忆召回文档](../memory_recall/README.md)）。

这样划分的原因：记忆越多，全量检索越容易召回无关内容、也越慢。把长期不用的记忆移出默认范围，召回质量更稳，object 库也不会持续膨胀。object 另有 `forgetfulness` 标记（`0` 长期保留 / `1` 允许随时间淡出），由提取阶段判断这条记录是否值得长期占据默认范围。
