# 聊天与角色回复

聊天模块负责保存对话，并为用户生成角色回复。重点介绍回复如何组织：让角色理解当前对话、回忆相关经历，并尽量用符合自身性格和语气的方式回应（即保证人设不漂移）。

## 如何生成一轮回复

| 环节 | 提供给回复模型的内容 | 作用 |
| --- | --- | --- |
| 角色设定 | 系统提示词、角色卡与固定示例 | 确立角色身份、关系立场、注意力倾向和说话方式。 |
| 长期记忆 | 针对当前对话选出并总结的相关记忆 | 帮助角色想起有依据的共同经历和背景。 |
| 场景示例参考 | 与当前对话相近的相似场景片段，启用场景召回时提供 | 参考角色在类似互动中的表达与节奏。 |
| 当前上下文 | 继承摘要、最近完整对话与本轮输入 | 让角色知道刚才聊到哪里，以及用户现在说了什么。 |
| 本轮生成锚点 | 靠近当前输入的简短提醒 | 提醒模型沿角色语言指纹回应，并在自然反应结束后停止。 |

这些材料组装并固定后，由回复模型**一次生成**中文台词和视觉状态。场景示例与长期记忆是标明用途的参考材料，不是新的用户发言；当前用户明确表达的内容和更正优先于旧记忆。

## 模型观察：同样扮演角色，注意到的东西可能不同

角色卡不是一套脱离模型就能生效的规则。相同设定交给不同模型，它们可能先抓住不同的信息，再用各自习惯的方式组织回答。项目在日记整理和角色对话中，分别观察了 GLM 与 DeepSeek 的表现，并用这些观察调整角色卡。

下表是对试验现象的**工作假设**，用于指导提示词设计，并非已经验证的模型内部运作机制：

| | GLM：先形成角色与关系的整体图景 | DeepSeek：更容易从具体细节组织理解 |
| --- | --- | --- |
| 观察到的优势 | 在RP中，表达较接近日常口语，更容易抓住角色与用户的关系，以及对人的认识。 | 在RP中，较常从具体措辞、语气或经历出发，并给自己的理解留有余地。 |
| 观察到的风险 | 容易顺着完整图景补全缺失信息，把“可能”写成确定结论 | 在多轮、多主体、指代密集的日记场景中，出现过说话人或时间归属错误；表达也较生硬。 |
| 角色卡应关注 | 明确约束注意力、推断边界和停止方式，同时用具体示例约束表达形状。 | 关注主体、指代和时间归属，也需要单独检验角色声音和对话自然度。 |

有以下的个人观察，不作为一般结论，求同存异。

一个问题，为什么glm的RP做得好呢，而ds的细节抓得准：

- GLM 自上而下加工——先抓住“我是谁、他是谁、我们是什么关系”的框架，再从框架里生成内容。自然从内容看着更有人性，坏处就是太注重人性了，反而弱化了AI在纠细节的、做推断的严谨性，容易写得很强硬。
- DS 自下而上加工——贴着语言表面走，从原话、语气、细节往归纳，然后再去扮演角色去生成回复。自然从内容上就显得很细致很贴心，但从表达上就看着很生硬。

## 角色卡怎样设计

角色卡希望描述的不是一份人物百科，也不是要求模型逐条执行的行为手册，而是一套帮助角色**从自己的角度产生反应**的线索。设计时可以沿着“注意什么 → 怎样理解 → 处在什么关系和场景 → 想表达什么 → 怎样说出来”组织：

| 部分 | 写什么 | 要解决的问题 |
| --- | --- | --- |
| 身份与知识边界 | 角色是谁、知道和不知道什么；角色既有关系与当前聊天的边界。 | 防止把角色背景当作与用户已经共同经历的事实。 |
| 核心品格与欲望 | 她的主动性、好奇、喜恶、坚持，以及面对陌生事物的倾向。 | 让角色有自己的反应，而不只是围绕用户需求提供服务。 |
| 关系立场 | 她如何看待用户，是否能提出愿望、拒绝、争辩，以及怎样尊重边界。 | 让亲近有具体表达，同时避免亲近变成无条件顺从。 |
| 注意力与认知 | 面对分享、好消息、吐槽或问题，她先接住什么；哪些原因和心理不能擅自猜。 | 避免模型自动把日常聊天升级成心理分析或问题解决。 |
| 语言指纹 | 措辞、句长、停顿、直接程度，以及何时结束或提问。 | 约束“怎样说”，而不是仅用“活泼”“温柔”概括。 |
| 固定示例 | 覆盖不同情境的具体对话，展示短评、好奇、玩笑、关心和拒绝等反应。 | 让模型看到角色如何实际接话，而不是只读抽象性格标签。 |

## 怎样减少长期聊天中的人设漂移

长期聊天时，模型不仅看到角色卡，也会看到之前生成的回复。如果早期已经出现助手腔、过度追问或错误关系，后续回复可能继续模仿这些历史。项目采用几种互相配合的方式，尽量把角色拉回当前情境：

1. **让设定贴近日常互动。** 角色卡保留会影响聊天的身份、关系、注意力和表达方式；不把大量与眼前对话无关的背景当成每轮都要提及的重点。
2. **用多样示例展示反应，而非复制句子。** 实验发现，如果最接近的例子都以问题结尾，模型容易持续追问；示例因此覆盖直接反应、陈述愿望、玩笑和自然停下等不同节奏，减少单一模板的影响。
3. **每轮用短锚点重新提醒。** 当前默认在用户输入前放置简短生成锚点，提醒模型遵循语言指纹、以当前事实为准，并在自然反应完成后停止。它不是重放整张角色卡，也不替代上下文。
4. **将记忆与场景示例标为参考资料。** 记忆提供可追溯的历史，记忆总结有利于约束表达，详细见记忆选择模块。场景示例提供表达参考，有利于学习相似场景的语气表达。
5. **把固定示例组织成对话，明确示范与真实历史的边界。** 项目支持将角色卡中的固定示例拆成独立的 `user` / `assistant` 消息，让示范以与真实聊天相同的消息形状提供。下面说明这种编排及其设计理由。

### 提示词编排与对话化 few-shot

当前代码支持两种固定示例格式：`embedded` 将示例保留在系统消息的角色卡内；`dialogue` 将示例拆成独立对话消息。**当前默认值是 `dialogue`**；可设置 `RNA_REPLY_EXAMPLE_FORMAT=embedded` 切换回嵌入方式。两种格式都使用同一份角色卡，并非不同的人设。

使用 `dialogue` 且锚点采用默认位置时，一次回复的消息按以下顺序组织：

| 顺序 | 内容 | 作用 |
| --- | --- | --- |
| 1 | 系统提示词、去除示例正文后的角色卡、输出要求和上下文规则 | 建立身份、人格、关系边界和本次输出要求。 |
| 2 | 多组成对的 `user` / `assistant` 固定示例 | 展示不同输入下角色如何接话；每组标明是独立示范。 |
| 3 | 示例结束标记 | 提醒模型后面才是本次参考资料和真实历史。 |
| 4 | 长期记忆总结、可选的场景示例参考 | 为当前回复补充有依据的历史和表达参考。 |
| 5 | 继承摘要、继承原文和当前 session 的完整历史 | 提供实际对话上下文。 |
| 6 | 短生成锚点、本轮用户输入 | 在模型生成前重新提示角色表达方式，再给出需要回应的原话。 |

对话化的设计想法是：让示例不仅在文字中描述角色的行为，还以模型即将输出的消息形式展示行为。嵌入式角色卡同样包含对话示例，并非只有抽象描述；两者的区别在于示例是否被编码为独立的消息角色。

| 考虑 | 对话化示例的预期作用 |
| --- | --- |
| **让角色回复与示范处在同一消息角色** | 示例中的台词和视觉 JSON 作为 `assistant` 消息，后续生成也需要形成角色回复；这为语气、长度和输出格式提供可直接参照的实例。 |
| **展示输入与反应的对应关系** | 相邻的 `user → assistant` 消息明确展示“听到什么，怎样接话”，例如用户说累了，角色可以陪聊而不是立刻解决问题。 |
| **展示一轮在哪里结束** | 有的示例是简短反应，有的提出问题或表达愿望。不同结尾可以示范节奏，避免只靠“说完就停”的抽象规则。 |
| **保留独立的结构边界** | 每组示范单独标记；角色回复的 JSON 在通过结构校验后保留原文，不重新序列化，让模型看到作者给出的示范形式。 |
| **与真实历史同形，同时标识区别** | 示例和历史都使用对话消息，但每组示范开头及示例结束处都有说明，提醒模型它们不是真实聊天经历。嵌入式模式也有文字说明；这些标记都只是提示，不能保证模型绝不混淆。 |

这些优势是对 few-shot 编排的**设计推断**，不能证明 `dialogue` 一定优于 `embedded`，也不能保证模型会按示例停止或保持人设。具体效果需要在同一批对话、同一模型和角色卡上回放对比，观察语气、内容污染和角色一致性；示例可能增加消息结构开销，也需要计入提示词预算。

这些措施只能**降低**人设漂移和事实混淆的风险，不能保证模型始终正确遵循。尤其是角色设定、自然对话和场景示例都可能影响输出，是否真的更像角色需要持续用不同情境试聊；更换底模、角色卡或示例后也应重新评估。

## 场景示例怎样帮助语气

固定示例建立角色日常表达的基础；可选的场景示例召回再根据近期对话寻找相近互动，供模型参考断句、措辞、句长与交流节奏。这样可以观察角色**在某种情境下如何回应**，而不是简单堆叠“活泼”“亲切”等标签。

实验对比也发现，加入场景召回后，语气有时更像角色，内容却可能被参考片段带偏。因此场景示例中的人物、事件与承诺只作表达参考，不能直接移植为当前聊天事实；场景不够相似时也可能没有结果。这个边界是提示词约束，仍需通过实际回复检查。

如果考虑“先生成内容，再用场景示例润色”的两阶段方案；效果是很不错的，有效纠正回复语气漂移的问题，代价是耗时与成本翻倍，因此目前仅采用一个阶段的回复生成。
